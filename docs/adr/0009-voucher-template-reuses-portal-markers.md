# The Voucher template reuses the Portal's marker mechanism

An Operator should be able to change printed Vouchers with plain HTML, CSS and
an optional script, without learning Go templates or rebuilding the Controller.
The Print sheet therefore reuses the split from [ADR 0004](0004-portal-is-operator-editable-static-files-over-json-api.md):
Operator-owned presentation, Controller-owned data and marker binding. This does
not change redemption, Device identity or the Router's role as sole meter.

## Decision

A Voucher template contains `voucher.html`, `voucher.css` and `custom.js`.
The shipped default lives in the binary, not the ledger. The editor follows
the Portal files pattern: draft, published and previous slots; no published files
means use the embedded default. Preview uses the same renderer with draft
files and a sample batch.

The Controller writes formatted batch data and Voucher codes into a
`script[type="application/json"][data-voucher-batch]` element. It inlines the
HTML and CSS, then its immutable `voucher.js`, then the template's `custom.js`
in a separate script element. After custom.js has had a chance to subscribe,
voucher.js clones the single `[data-voucher="card"]` once per Voucher, fills
markers with `textContent`, and dispatches `voucher:rendered` on `document` with
the complete data as `event.detail`. A throwing custom.js cannot stop binding.

Version 1 marker names are stable Operator contracts:

- Required: `card` (exactly once, outside head) and `code` (exactly once inside card).
- Optional: `time`, `pesos`, `validity`, `pause-limit`, `shop`, `seller`, `batch`,
  `created`, `used`, `qr`.
- `time` and `validity` are readable durations, `pesos` includes ₱ (blank for an
  unknown legacy price), `pause-limit` and `batch` are decimal numbers, and
  `created` is the batch creation date/time formatted in the Controller's local
  time. Blank Seller means Shop.
- `used` is `USED` or blank; redeemed cards also receive `data-used`.
- `qr` alone is filled with `innerHTML`: SVG generated by the Controller from
  the configured Portal URL, never Operator or ledger HTML. The small pure-Go
  `rsc.io/qr` encoder supplies the module grid, drawn with a four-module quiet
  zone. It opens `/portal`, without code pre-fill.

Batch fields are the purchase snapshot from [ADR 0008](0008-voucher-batch-carries-purchase-terms.md),
not today's Rate tiers. Reprinting includes redeemed Vouchers and marks them used.
`shop` comes from the Shop name setting, defaulting to OpenPiso WiFi. It is
saved separately from template drafts and takes effect immediately.

## Security and editing

The sheet is self-contained: no CDN, external fonts, images or network calls.
Its CSP uses `default-src 'none'`, per-response nonces for scripts,
`style-src 'unsafe-inline'`, `img-src data:`, `connect-src 'none'`,
`form-action 'none'`, `frame-ancestors 'none'` and `base-uri 'none'`.
Scripts from template HTML are removed; scripts belong in custom.js. Batch JSON
is escaped by Go's JSON encoder, and only the two Controller-inserted executable
scripts receive the nonce. Inline event handlers are not authorized.

The editor's save check enforces required marker positions and counts,
rejects external URLs and files over 64 KB, and directs HTML script authors to
custom.js. Browser preview, draft/publish, Revert and Reset follow the Portal's
workflow; server-side JavaScript execution or validation is not added. As in
the Portal editor, Reset changes what is published without discarding the draft.
The first publish remembers the shipped default as previous (version zero,
without storing its files), so Revert can undo the first publish too.

## Consequences

- The default prints fixed 62 × 44 mm cards, three across on A4, with
  `break-inside: avoid`. The screen grid reflows; browser Print supplies PDF.
- JavaScript is needed to render cards, but custom.js is optional and isolated
  from the Controller script. The event lets it colour prices and wire Print.
- The renderer accepts the three files independently of storage so adding the
  editor does not change the Print sheet contract.
- Lab E2E checks cards, event delivery, used reprints, CSP, self-contained loads,
  throwing custom.js and a report screenshot. Codes come from CSV rather than
  the template's layout.

## Alternatives considered

- A fixed Go print template is simpler but cannot be edited without a rebuild.
- Editable Go templates introduce a second template language and a larger trust
  boundary. Plain markers keep rules and escaping under Controller control.
- Letting custom.js clone cards would make printing depend on Operator code.
- A separate PDF renderer adds another layout engine; browser Print is enough.
